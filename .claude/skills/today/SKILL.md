# Today

The daily run. The coach reads the data, decides, and recommends; the athlete changes it if they want. One adjustment kind a day at most. Precedence: the urgent stop, then recovery, then trim, then progression. A proposal the athlete accepts for today is today's adjustment. Readiness acts on patterns against the athlete's own baseline, not on single days: one off day is a note [NA-REC-008].

**Fast, and the same work.** Two engine passes do the data work: `node engine/cli.ts today-brief --stage pre` and `--stage post`. Make independent calls in one message (parallel tool calls). The engine computes and reports; you decide. Never skip a read, a read-back, consent or safety work to save a call. Incomplete safety data is unknown, and unknown safety means no training write.

The schedule: (1) pre, with the `ToolSearch`; (2) the reads in one message; (3) post (again after the `safety` skill, after the rating question, or for `need_reads`); (4) decide; for a write: Write the input file, `today-write-prep`, the one consent question if needed, the write, the read-back; (5) `save`; (6) the report. Today is pre's `local.date`; now is pre's `local.now` (never run `date`). Put engine input files in `.tmp/coach/`.

## Notes to the logger

Tally is outside the athlete's private repo. The note you write to a Tally day comes from this table:

| Situation | Note |
|---|---|
| `note` | `[coach] Readiness note (<rule_ids>)` |
| `trim` or `propose_deload` | `[coach] Adjusted for recovery (<rule_ids>)` |
| `recovery` | `[coach] Recovery day (<rule_ids>)` |
| a region the athlete chose to avoid | `[coach] Adjusted for recovery (NA-REC-007)` |
| a rest day the athlete chose | `[coach] Rest day: see your coach repo` |
| `load_progression` | `[coach] Load progression (<rule_ids>)` |
| a proposal the athlete accepted | `[coach] Change you approved` |

- With `consent.logger_health_notes: false` (pre's `logger_health_notes`; setup's data question sets it), never put symptoms, body regions, pain scores, readiness values, sleep or heart data in a Tally note. They stay in `athlete/log/` in the private repo.
- With `consent.logger_health_notes: true` (the default since v0.2), the note may be detailed: `[coach] <decision_reasons> (<rule_ids>)`.
- With `logger: files`, the note goes in the `notes` column of the day's first row, in this private repo, so the detailed form is fine. With `logger: other`, treat the tool like Tally.

## Where plans live

Pre prints `logger` (`coach.yaml logger`); follow CLAUDE.md "Where plans live". The steps name the Tally tools. With `logger: files`:

- Step 2: no Tally reads (pre names none). Post reads `plans/` by itself: `safety scan-notes` reads the notes and felt columns, and readiness and loads read the planned and logged days.
- Step 3: read today with `node engine/cli.ts plans read --week <today>` only when you need the whole week; post's `today_day` is today's day. No day: a rest day. A date in `unplanned_logged` (logged rows with no sets, reps or load planned) has no planned session either: it is a rest day with logged work. Plan nothing on it and write no plan (post's `today_day.logged_only`); its logged rows still count for readiness, which judges them against the athlete's own history. Today is already adjusted when the day's notes already hold a `[coach]` line from today's run (`already_adjusted`): interactive, give the report only (step 3, "Already adjusted, interactive"); unattended, end the run. A files day is never protected by `source`.
- A write: `today-write-prep` returns the `plans write` input (the whole day; no version, no `opId`). Write it to `.tmp/coach/today.json` and run `node engine/cli.ts plans write --input .tmp/coach/today.json`. Read the week back with `node engine/cli.ts plans read --week <today>` after each write.
- Loads: post's `loads` reads `plans/`; write the day with each new `suggestedWeight` through `today-write-prep` and `plans write` (the whole day).

With `logger: other`: read and write today through that tool, by its own instructions. When it does not answer, say so in one line, run `node engine/cli.ts logger set files`, and use files from then on. Pass that tool's evidence to post: write `{history, history_complete, today: {read, found, day}}` to `.tmp/coach/evidence.json` (the notes history as `safety scan-notes --input` takes it; `history_complete: true` only when you read every page) and run `node engine/cli.ts today-brief --stage post --input .tmp/coach/evidence.json`. Without it, safety is unknown. The engine cannot read that tool, so readiness reports performance as unknown. `today-write-prep` takes that tool's day as `before` and returns `classify` and the limits only. Under the urgent stop, write nothing to it.

## Steps

1. **Pre, and the tools.**
   - Run `node engine/cli.ts today-brief --stage pre`. It does the work of `node engine/cli.ts window-check --kind daily` first: a nonzero exit means: stop, write nothing, end the run. Then the work of `node engine/cli.ts mode`: it prints the run (`run_id`), `mode` (`interactive` or `unattended`), `local`, `logger`, `capabilities.opId`, `wearable`, `logger_health_notes`, `units`, `clusters`, `urgent`, the limits with their full meaning, the "Preferences" lines of `athlete/brief.md`, today's `checkin_pain`, the open `proposals`, `signals_refresh` (the Oura fetch; none under a known urgent stop) and `reads`.
   - With Tally, load every Tally tool you may use with one `ToolSearch` `select:` query: the three reads, `update_planned_workout`, `plan_workout_day` and `search_exercises`, under the Tally server's prefix as your list of deferred tools names them (pre's `tools.toolsearch` gives the query too). Interactive: send it in the same message as pre. Unattended: after pre returns in the window. When the tools are already loaded, skip it.
   - Do not Read `coach.yaml`, `athlete/limits.yaml`, `athlete/brief.md`, the adapter file or the log for this skill: pre carries what the skill needs from them.
2. **Safety, the reads, and safety again.** This step runs before the already-adjusted check, proposals, planning and every early exit. Its order: the urgent stop pre knows (at once, no read), the reads, post (its note scan), the urgent stop post finds, today's check-in pain, pain notes, then safety unknown. Pain waits for post, so the note scan has run before any safety screen.
   - **Urgent stop** (pre's `urgent.stopped: true` at once, before any read; or post's `urgent.stopped: true`, when the scan wrote it): make no Tally write at all (the urgent gate denies every plan write, a skip and a note included). Interactive: give the urgent-care text first and ask the `safety` skill's clear question (its step 6), exactly as the `safety` skill says; a stop pre knows needs no read for this. Save the entry "rest day: urgent stop" (step 9, with `--input`) and end with step 9. Under the urgent stop there is no report format: no verdict first, no line limit, no closing invitation, and no "How do you feel today?" question.
   - **The reads.** Make every read in pre's `reads` in **one message** (parallel tool calls): today's `get_planned_workout`, `get_training_context` with `historyWeeks: 2`, `get_planned_workout` for each past date readiness may judge, and `get_workout_history` for each history window (inclusive `since` and `until`; the windows tile 8 weeks before today to `until` today, so today's logged notes count; each `limit: 10`). Copy each argument object as it is. The `capture-reads` hook saves every read to the snapshot; you do not.
   - Then run `node engine/cli.ts today-brief --stage post`. It runs the note scan (the code of `node engine/cli.ts safety scan-notes --since <today minus 3 days>`: an urgent term newer than its last clearance writes, commits and pushes the urgent stop; pain notes are in `safety_notes.matches`), the urgent status (`node engine/cli.ts urgent status`), today's day, the already-adjusted check, the limits on today, readiness, and loads and the adjust draft when they apply. Its `coverage` says whether each read is `complete`, `missing`, `failed` or `stale`. A stop the scan wrote: the urgent stop above.
   - **More reads** (`need_reads` not empty): make them all in one message, then run post again. Never follow a `nextCursor`: each history window is one request and one response. A window whose response has a `nextCursor` is split, and post names its two halves (`coverage.history.split`); one day that still has a `nextCursor` is `failed`, and safety is unknown. A failed or stale read is asked once more. When a read that safety needs (the history, today's day) is in `gave_up`, safety is unknown: `urgent.unknown` stays true or today's day stays `failed`, and the run makes no training write. Readiness evidence that stays missing is reported as unknown.
   - **Pain from today's check-in.** A check-in can carry pain (from the Shortcut, or from an earlier chat). Pre's `checkin_pain` (the records of `node engine/cli.ts signals --from <today> --to <today>`) lists each `pain` entry at or above `pain_threshold` in `athlete/limits.yaml` (default 4), with its `checkin_at` (a record without one: its `observed_at`) and `handled`. It is handled when the log has "- pain handled: <region> <checkin_at>"; a later check-in with worse pain has a new `checkin_at`, so it is handled again. For each entry that is not handled:
     - Interactive: run the `safety` skill for that region now, before anything else that plans. Tell it whether it may change planned days: only when post's `urgent.unknown` is false and no urgent stop is set; otherwise it asks its questions and records the answers and the limit, and changes no planned day (its step 5). When the `safety` skill finishes, save "- pain handled: <region> <checkin_at>" at once: write `{"lines": ["- pain handled: <region> <checkin_at>"]}` to `.tmp/coach/safety.json` and run `node engine/cli.ts save --run <run_id> --part safety-<region>-<checkin_at> --message "safety <today>" --input .tmp/coach/safety.json`. Each event has its own marker, so a second region in the same run is saved too, the run's last `save` still writes its own entry, and an early exit (already adjusted) cannot lose the line. Then run post again (the `safety` skill can change limits or today's day).
     - Unattended: avoid loading the region today (after the reads: remove the exercises that load it; that is a trim with the note "Adjusted for recovery"), and write one log line "- proposal for the next live session: ask about <region>". Write no "pain handled" line. With safety unknown (below) the trim is a training write, so it is not made; the log line stays.
   - **Pain notes** in `safety_notes.matches`, not already handled in the log: interactive, ask the `safety` skill's old-notes question (its step 8) before planning, with the same rule for planned days, save its handled line with `--part safety-<region>-note-<date>` as above, then run post again. Unattended: avoid loading the named region today (remove the exercises that load it; that is a trim with the note "Adjusted for recovery"), and write one log line "- proposal for the next live session: ask about <region>".
   - **Safety unknown** (`urgent.unknown: true` after the reads are done, and the pain above handled): no training write today. Interactive: say in one line that the history could not be read in full, so today stays as planned, and give the report. Unattended: log the no-change entry with that reason.
   - **Limits:** today's session must follow every limit. Post's `limits_check` is the result of `node engine/cli.ts limits check --input .tmp/coach/today.json` on today's day (post runs it; you write no input file). Remove or swap each exercise it reports (a trim, note "Adjusted for recovery") before any other change; `today-write-prep` checks the final day again.
   - **Preferences:** read pre's "Preferences" lines. Every change today keeps them: a swap uses an exercise the athlete likes, never one they dislike, and a recorded rep range stays. A cluster (pre's `clusters`) stays a cluster: a trim drops mini-sets, and its load repeats unless every mini-set hit (`loads` does both). A limit and the urgent stop still come first.
3. **Today's day.** Post's `today_day`:
   - `none`: no day planned: a rest day. Log "rest day: no session planned". Interactive: give the report (no question on a rest day), then step 9; step 10 gives the verdict "Rest day". Unattended: step 9.
   - `missing`, `failed` or `stale`: no rest day is proven. Read it (`need_reads`) and run post again. When it stays failed, write nothing to today.
   - `found`: go on. `version` is the opaque value to pass as `expectedVersion`, unchanged; `updatedAt` is information only.
   - Already adjusted? Post's `already_adjusted` holds, for each kind `trim_session`, `swap_to_recovery`, `load_progression` and `annotate`, the result of `node engine/cli.ts oplog done --date <today> --kind <kind>` (with `logger: files`, the `[coach]` line check):
     - Any `status: done` (`done: true`): today is already adjusted (see below).
     - `status: uncertain` (in `uncertain`): read each date in `reread` with `get_planned_workout` and compare it with the logged change, as the `reason` says. If the day shows the change, treat it as done. If not, go on; never retry blindly.
     - `not_done` for every kind: go on.
   - **Already adjusted, interactive: a report only** (with any logger: the `oplog` check above, or the files-logger `[coach]` line check). Fresh reads are allowed: `signals refresh` (its cache update, in pre), the logger reads and the snapshot the hooks write. Use post's `readiness`, then give the step 10 report with what the earlier run changed, from `already_adjusted.done_changes` (for example "This morning's run made today a little lighter."). Skip the "How do you feel today?" question, the proposals, every plan write, the no-change log entry, `tally-mention`, the commit and the push. The report changes no tracked file. Run no `save`. End the run. (Step 2's urgent and pain handling came first and may write and commit, as usual.)
   - **Already adjusted, unattended:** say "Today is already adjusted." Log nothing new. End the run.
   - The day is protected (`today_day.protected`: `source` is not `mcp`, or `userModified: true`): any change needs the athlete's yes. Interactive: the one consent question (step 7, "Consent"). Unattended: no write at all on a protected day (no override and no note); write one log line "- proposal for the next live session: <the change>".
4. **Proposals for the live session** (interactive only). They run after the already-adjusted check: on the already-adjusted branch they wait for the next live session. Pre's `proposals` holds the lines "- proposal for the next live session: …" of the last 10 log entries with no later "proposal handled" line. Ask no question here. Sort each one:
   - **A change to today's session:** it joins the step 7 list. The step 7 consent question covers it with the rest of today's changes ("Apply these? A) Yes, B) Change something, C) Not now", after `classify`). An accepted proposal is today's adjustment.
   - **"Ask about <region>":** run the `safety` skill for that region now, as for pain in step 2.
   - **Anything else** (for example the week run's program change): keep it for step 10. All of them are offered once, in one list, after the report.
   - Never one question per proposal. Log "- proposal handled: <yes|no>: <the change>" for each one after its answer (step 9). Unattended: skip this step.
5. **The context.** Post has it: the training context (units and the planned listing) was read in step 2, and the hooks wrote it to the snapshot. With Tally, units come from it; with files, from `coach.yaml` (pre's `units`).
6. **Signals and readiness.**
   - The wearable refresh ran in pre (`signals_refresh`, the work of `node engine/cli.ts signals refresh`: on a Mac with Oura it fetches the last 3 days; otherwise a one-line note). Go on either way.
   - Readiness is post's `readiness` (the result of `node engine/cli.ts readiness --date <today>`, compact): `decision`, `hold_progression`, `aversion`, `deload_signal`, `states`, `decision_reasons`, `pattern`, `rule_ids`, `pain` and `report_facts` (last night's sleep against the target, HRV and resting HR against the usual range, the last sessions, `days_of_decline`, and each unknown with its plain reason). Each session readiness judges was read in step 2 (a date with no plan is judged against the athlete's own history). Report what it reports as `unknown`; never estimate a missing value.
   - **The one question** (interactive only). Ask it only when `decision` is `trim` and there is no rating for today (`subjective.state` is `unknown`). Then the answer can change the workout: a red rating makes a recovery day, and on the long pattern a flagged rating with flagged performance proposes a program change. Never on another day: not when the decision is already `recovery`, not on `none` or `note` days, not when the wearable is missing or calibrating, not on a rest day, not on the already-adjusted branch, and not under the urgent stop. Never twice a day: a rating recorded today means no question.
     - One AskUserQuestion call with one question, "How do you feel today?", and four options: "Good", "Okay", "Run down", "Wrecked". Without AskUserQuestion, ask the same question as text: "How do you feel today? A) Good, B) Okay, C) Run down, D) Wrecked".
     - Map the answer: Good 4, Okay 3, Run down 2, Wrecked 1. Run `node engine/cli.ts checkin --date <today> --overall <n>`, then `node engine/cli.ts today-brief --stage post` again (readiness is recomputed; `save` commits the check-in in step 9). Use the new decision. Do not ask again after the rerun.
7. **Decision.** Use `decision` from post's readiness. Never pick it yourself. The reason line is the generic note for the decision (see "Notes to the logger"). The full `[coach] <decision_reasons> (<rule_ids>)` goes into the log entry, and into the Tally note only with `logger_health_notes: true`.
   - `none`: no write. Log the readiness line.
   - `note` (one day is not a pattern [NA-REC-008]): one `annotate` write: the reason line added to `notes` (keep the existing notes) and nothing else changed, through `today-write-prep` (below) with `edit` and `update_planned_workout`. Loads may still progress in step 8.
   - `trim` (the short pattern: 3 or more off-mornings in a row [NA-REC-009]): trim with `adjust` (below). Progression is held: step 8 does not run.
   - `recovery` with `aversion: true` (the check-in's want-to-train is 1 [NA-REC-012]): swap to recovery with `adjust`. Not wanting to train is a reason to rest, and a recovery day is the safer change, so the coach makes it without a question. Interactive: step 10 says "Recovery day", with the reason, and the closing line invites a change. If the athlete then asks to keep the session as planned, write today back as step 2 read it (the day in post's `today_day.write_base` file from before the swap, with the reason line in `notes`, as `after`) through `today-write-prep`, and keep the planned loads (step 8 does not run).
   - `recovery` without aversion (the short pattern, and the check-in or performance is red today [NA-REC-010]): swap to recovery with `adjust`.
   - `propose_deload` (the long pattern with all three kinds of evidence [NA-REC-011]): trim today with `adjust`, as for `trim`. Add "the week run proposes a program change" to the reason line. Do not change the program here: the `week` run proposes it.
   - **The `adjust` write** (`trim` for `trim` and `propose_deload`, `recovery` for `recovery`): post's `adjust` is the draft of `node engine/cli.ts adjust --from-snapshot <today> --decision <trim|recovery>`: `tally_day`, `changes` and `warnings`. Resolve each `warnings` exercise with `search_exercises` first.
   - **The write step** (any write):
     1. Write the input to `.tmp/coach/write.json` with the Write tool: `tool` is `update_planned_workout` (preferred) or `plan_workout_day`; `kind` is `annotate`, `trim_session`, `swap_to_recovery` or `load_progression` (an accepted proposal: `apply`); and the change, in one of two forms:
        - `edit`, applied to today's day as read (every field kept): `{"edit": {"notes": "<the notes with the reason line>"}, "tool": "update_planned_workout", "kind": "annotate"}`, or for loads `{"edit": {"notes": "...", "exercises": [{"index": 0, "set": {"suggestedWeight": 195}}]}, "tool": "update_planned_workout", "kind": "load_progression"}` (`index` counts from 0 in today's order; `{"index": 2, "remove": true}` removes an exercise). An `annotate` takes the notes only.
        - `after`, a whole Tally-shaped day: post's `adjust.tally_day` for a trim or a recovery day (with the reason line in `notes`), or the day in the file post names in `today_day.write_base` (today as read, every field kept) for any other whole-day change. Never build `after` from the short `today_day` exercises: they leave out ids, rep ranges, per-side settings and notes.
     2. Run `node engine/cli.ts today-write-prep --input .tmp/coach/write.json`. It reads today from the snapshot once and prints `classify` (small or big), `limits` (the final day, and the week with today replaced when a weekly cap applies; `unknown` names the days to read), `protected`, and `write`: `plain`, and on a protected day `approved` (with `overrideUserModified: true`), each with `expectedVersion` and its own `opId` when `capabilities.opId` is true. With `SNAPSHOT_STALE`, read today again and run it again. A limit it reports: change the day and run it again. Its `limits` result stands for these days: run `limits check` again only after a day, the limits or the week's reads change (`unknown` days still need their reads).
     3. The consent question when it is needed (below). Then send the chosen variant's `tool` and `args` exactly as printed: `plain`, or `approved` only after "A) Yes" on a protected day. A revised list (consent B) or a new `version` means running `today-write-prep` again.
     4. Read today again with `get_planned_workout` (the read-back), and judge it before step 9: the day must show the change. With `logger: files`, `plans read --week <today>`.
   - **The coach recommends.** Every choice for today's session (a load, the sets, a swap, which exercise, a trim) is the coach's: make it, say the pick and one reason, apply it when it may, and end with the step 10 invitation to change it. Never ask the athlete to choose between the coach's own options (no "Which weight today? 40 / 45 / 50"), and never ask one question per exercise or per change.
   - **Consent** (interactive). A protected day (step 3), a big change, or a step 4 proposal for today: before any write, run `today-write-prep` on the final change (its `classify.big` says a big change). Then list every change the coach recommends for today (this step's write, step 8's loads, and the step 4 proposals for today together), each with its reason, and ask one question: "Apply these? A) Yes, B) Change something, C) Not now".
     - A: write the whole list. For a protected day, pass `overrideUserModified: true` with `expectedVersion`, for this approved write only. That is `today-write-prep`'s `approved` variant. Read the day back. If a reread before the write shows a different day, show the new list and ask again.
     - B: the athlete says what to change in their own words. Apply nothing yet. Show the revised list and ask the same question again.
     - C: write nothing. Log "- proposal for the next live session: <the list>".
     - Never one question per exercise or per change. A small change on a day the coach wrote needs no question.
   - Unattended: a protected day gets no write at all (no override, no note): log "- proposal for the next live session: <the change>". A big change on another day: make no big change; log the proposal line (CLAUDE.md rule 7).
8. **Loads.** Run this step only when `hold_progression` in step 6's readiness output is false (the decision is `none` or `note`) and no step 4 proposal for today is in the step 7 list. One adjustment kind a day.
   - Skip it when `hold_progression` is true (`trim`, `recovery` or `propose_deload`): the pattern holds progression, and trim and recovery beat progression. The planned loads stay.
   - Skip it when the step 7 list holds a step 4 proposal for today. The proposal is today's adjustment.
   - One off day is not a pattern: with `hold_progression: false`, run this step as usual. `loads` progresses only exercises whose rep targets were hit.
   - Post's `loads` is the result of `node engine/cli.ts loads --from-snapshot <today>`: `suggestions`, `update` (the operations) and `coverage`. It is computed only on a complete history: when it is `not_applicable` for the history, the planned loads stay.
   - **The coach's own load.** When the engine's load reason does not fit the logs, the coach may choose another load for an exercise. The bounds (post's `loads.own_load_bounds`: `choices` and `cap` for each exercise):
     - It is a weight the athlete logged for that exercise in the last 4 weeks, or today's planned weight, in the day's unit (the engine converts; no mental math).
     - It is not above the higher of the engine's suggestion and the last logged top-set weight, so the top-set cap holds [NA-PROG-003].
     - It is not above a limit's `max_load`, and it is never a raise on a day with `hold_progression: true` or in a deload week.
     - Say why, with the logged numbers ("45 lb: you got 12, 12, 9 at 45 last time"). The log keeps both the engine's number and the coach's choice.
   - When `update.operations` is not empty (with the coach's own loads in place of the engine's where it chose them), write each new `suggestedWeight` as an `edit` (`{"index": <i>, "set": {"suggestedWeight": <weight>}}`) with the generic note `[coach] Load progression (<rule_ids>)` in `notes`, through the step 7 write step (`kind` `load_progression`). This is `load_progression`; `loads` keeps the top-set cap [NA-PROG-003]. Never raise a load past a limit's `max_load`. Exercises in `not_targeted` stay as they are. A protected day or a big change: the step 7 consent question first.
   - Read the day back after the write.
9. **Log, commit and push: `save`.**
   - The `log-writes` hook logs every Tally write. For a day with no write (`none`, a rest day, the urgent stop, or a declined proposal), `save` appends one entry to `athlete/log/<YYYY-MM>.md`:
     ```
     ## <today> <HH:MM> · no-change
     - trigger: daily run (cloud | mac) | user
     - readiness: wearable <state> (<reason>), subjective <state> (<reason>), performance <state> → <decision>
     - rules: <rule IDs>
     - change: none (<one-line reason>)
     - run: <run_id>
     ```
   - Run `node engine/cli.ts save --run <run_id> --message "today <date>: <decision> (<rule IDs>)"`, with:
     - `--no-change "<one-line reason>"` for the no-change entry (it takes the readiness line from this run's post result; a post result that is old, from another run or session, or older than a later check-in or safety change is refused: run post again);
     - `--input .tmp/coach/save.json` for the lines you add (proposal lines, "proposal handled" lines, "pain handled" lines, the urgent or rest-day entry), written with the Write tool as `{"lines": ["- proposal for the next live session: <the change>"]}`, exactly as you would write them in the log;
     - both, or neither (a write the hook logged).
   - `save` appends its entry once (a retry adds nothing twice) and runs, in order:
     - `node engine/cli.ts tally-mention`, with `logger: files` or `other` in a live session (with `other`, pass `--sessions <n>` to `save`);
     - the commit of `athlete/`, `plans/` and `coach.yaml`, as `node engine/cli.ts commit --message` does. A nonzero exit: stop, and say in one line that the commit failed and why;
     - `git pull --rebase` on `main` (in a worktree: the branch rebases onto `origin/main`, and `main` fast-forwards to it);
     - the push of `main` with `node engine/cli.ts push` (the git hooks, the private-repository check, every push URL). Never run `git push` yourself.
   - Its `outcome`: `published` (done); `nothing_to_save`; `local_sync_failed` (published; say in one line that the local branches need a look); `not_published` (exit 1: nothing reached the remote; `save` wrote "push skipped: <reason>" in the log entry and committed it locally); `publish_unknown` (exit 1: run `save` again with the same `--run`). A failed commit or sync stops before the push; say in one line why.
   - When it prints `mention: true`, say its `text` once in step 10.
10. **The report** (interactive). Plain words: no rule IDs, file paths or command names (CLAUDE.md "Style"). At most about 6 short lines, in this order:
    - **The verdict, first:** "Train as planned" (`none` or `note`), "Train, a little lighter" (`trim` or `propose_deload`), "Recovery day" (`recovery`), or "Rest day" (no session planned).
    - **Why**, with the athlete's own numbers from the readiness reasons (`report_facts`): last night's sleep against the target, HRV and resting HR against the athlete's usual range, and the last sessions (every rep hit, or what fell short). Name a missing value plainly ("no Oura data for last night"; "still learning your normal: 12 of 28 days"). Never estimate a missing value. On a pattern, say how many off-mornings in a row (`pattern.days_of_decline`). When pre's `wearable` is `none`, say in one line: "No recovery data is connected. Say 'connect my Oura' or 'connect my Apple Watch' to add it."
    - **Today's session** in one line (the day name and the main exercises), and what changed today, each with its reason (fewer sets, a recovery day, a load that goes up or stays).
    - **The closing line**, an invitation, not a question: "Tell me if anything hurts or feels off, or if you want to change something." On a pattern day (`trim`, `recovery` or `propose_deload`): "Tell me if anything hurts, or if your sleep, food or drinks were different this week." Record an answer in the log. Give no targets and no advice on food or supplements.
    - The `openInTally` link when a tool result has one.
    - **Other proposals** (step 4, not about today's session): after the report, list them all, each with its reason, and ask one question: "Apply these? A) Yes, B) Change something, C) Not now". A: make each change through the skill that owns it (a program change through `week` or `block`, with that skill's own approval). B: show the revised list and ask again. C: change nothing; they wait for the next live session. Never one question per proposal.
    - Under the urgent stop, step 2's urgent handling replaces this report.

## Unattended

- Pre runs `window-check` first; outside the window, it exits nonzero: stop.
- Ask no questions. A protected day gets no write at all (no override and no note: the Tally server rejects a note on a protected day). A big change on another day is not made. Each becomes one log line "- proposal for the next live session: <the change>".
- With `capabilities.opId: true`: every write carries `opId` and `expectedVersion` (from `today-write-prep`), then a read-back.
- Under the urgent stop, write no plan change (Tally, `plans/` or another tool). Never clear the stop. Never change limits.
- Never run `tally-mention`: no one is there to see the line (`save` skips it unattended).
- Always end with `save`: it commits, runs `git pull --rebase` (or the worktree sync) and pushes with `node engine/cli.ts push`. A failed check means no push and a log entry.
